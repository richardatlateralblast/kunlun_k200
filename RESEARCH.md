# RESEARCH.md

Findings specific to running this exact K200 card and driver on a modern host (kernel 6.15+, including 7.0; gcc 14+), and to what software can actually use it today. Kept separate from `README.md`, which documents the repo's original S0–S9 driver-tuning work and benchmark baselines on kernel 6.8. Start here before new work on this card; it records what's confirmed, what's broken, and what's genuinely open, so it isn't silently redone or contradicted.

Dates below are when each finding was made, not when the underlying software shipped.

## Hardware and software generations (context for everything below)

Kunlunxin's cards are not one driver line with version numbers — each silicon generation has its own driver and, increasingly, its own software ecosystem:

| Generation | Chip | Cards | Driver/SDK line | Current official software support |
|---|---|---|---|---|
| Kunlun1 (KL1) | — | **K100, K200** (this repo) | `4.33.0` (this repo, patched for kernel 7.0), older `1.1.0` package line also seen in the wild | Mainline Paddle versions after 2.3 reportedly dropped it (unconfirmed, see below); no vLLM; FastDeploy doesn't list it |
| Kunlun2 | — | R200, R300 | separate, newer | Current PaddleOCR/PaddleX XPU docs target this and P800 |
| Kunlun3 (KL3) | — | **P800** | newest, `xpytorch` (KL3-customized PyTorch) | Target of `vllm-kunlun`, current `paddlepaddle-xpu`/FastDeploy releases |

Nothing found in this investigation contradicts the conclusion that **K100/K200 is two full hardware generations behind what Baidu's current LLM-serving software targets**. Treat any official Kunlunxin software released from 2026 onward as written for P800 unless it explicitly says otherwise.

## Driver: building for kernel 6.15+/7.0

Full step-by-step instructions are in `docs/BUILD-linux-7.md` and the README's "Building on Linux 6.15 / 7.0" section; this is the summary of *why* each change was needed, found by building on a Dell R730 (kernel `7.0.0-38-generic`, gcc 15.2) from a stock clone of this repo.

- **Build-system breakage, not kernel-API breakage, caused most of the ~225 initial compile errors.** Two separate causes:
  - Kernel 6.15+ ignores `EXTRA_CFLAGS`, and this driver's `Kbuild` puts every include path and `-D` define there. Fix: forward it to `ccflags-y`.
  - The conftest feature-detection probes compile without `-fms-extensions`, which kernel 7.0's headers need; every probe that pulls in `pci.h` or `scatterlist.h` then fails on `static assertion failed: sizeof(struct filename) % 64 == 0`, and the driver silently takes 6.8-era fallback code (`mmap_sem`, `vm_fault.virtual_address`, 8-argument `get_user_pages`). Fix: add `-std=gnu11 -fms-extensions` to the conftest's own `NV_CONFTEST_CFLAGS`, found by redirecting the conftest's `$CC ... 2>&1` (normally discarded) to a log file.
  - A secondary issue: the "function is present" conftest probes are logically inverted (success = absent) and rely on an *implicit declaration* being only a warning. gcc 14+ makes that a hard error by default, so several functions (`phys_to_dma`, `dma_is_direct`, `acquire_console_sem`, `jiffies_to_timespec`, `unsafe_follow_pfn`) were wrongly detected as present. Needed `-std=gnu11` (gcc 15 defaults to C23, which also breaks this) and `-Wno-error=int-conversion`.
  - gcc 13 is not a workaround: it passes the probes, but kernel 7.0's own build uses `-fmin-function-alignment`, which gcc 13 rejects.
- **Six genuine kernel API changes**, patched in source (13 files, ~30 lines): `in_irq()`→`in_hardirq()`; `del_timer()`→`timer_delete()` (6.15); `hrtimer_init()`+`.function=` →`hrtimer_setup()` (6.15); `nth_page(p,j)`→`p+j` (6.17, safe here because the pages come from one contiguous allocation); `follow_pfn()`/`unsafe_follow_pfn()`→`follow_pfnmap_start/end()` (6.12); `dma_map_ops.map_resource` removed (peer-DMA capability check now returns false).
- **Stubs for the gcc-14-broken probes above:** `phys_to_dma` falls back to the plain physical address; `dma_is_direct` assumed false; the console-lock and `jiffies_to_timespec` branches disabled; `vm_flags_set`/`vm_flags_clear` always used (`vm_flags` has been const since 6.3). These were written as *untested guesses* and flagged as a correctness risk — **since confirmed correct**, see "Confirmed working" below.
- **Result:** `make modules CC=<gcc -std=gnu11 wrapper>` → `kunlun.ko` (vermagic matches `uname -r`, no unresolved symbols), `kunlun_peermem.ko`.

## `scripts/install_driver.sh`/DKMS: suitability review and reboot-survival test (2026-10-19)

Reviewed `scripts/install_driver.sh` and `kunlun-driver/dkms.conf`, then exercised both the hot-reload and reboot paths on the just-reinstalled R730 host.

**It is not actually DKMS, despite the naming.** `dkms.conf` exists but nothing in this repo — not the script, not the `Makefile` — ever calls the `dkms` binary (`dkms add`/`build`/`install`). `/lib/modules/$(uname -r)/updates/dkms/kunlun.ko` is just the path Baidu's original installer historically placed the module at (presumably via real DKMS back then); this repo's script hand-copies into that same path and runs `depmod -a`. Confirmed on this host: `dkms` isn't even installed (`dkms status` → command not found), no `/usr/src/kunlun-module-dkms-*`, no `/var/lib/dkms`. Boot-time auto-load still works without real DKMS, because `kunlun.ko`'s `MODULE_DEVICE_TABLE` aliases cover this card's PCI ID and `depmod -a` is what lets `modprobe`/udev resolve that alias at boot — confirmed working below. The actual gap: with no real DKMS registration, **nothing rebuilds the module automatically on a kernel upgrade**; the installed `.ko`'s `vermagic` will stop matching and it will simply fail to load after the next kernel bump, silently, until someone manually reruns `make driver && make driver-install`.

**Bug found:** `install_ko_to_disk()` does `cp -a "$KO_SRC" "$KO_DST"` with no `mkdir -p` on the destination directory first. On this freshly reinstalled host, `/lib/modules/$(uname -r)/updates/dkms/` didn't exist yet (no prior real-DKMS install had ever created it), so the first run failed with `cp: cannot create regular file ...: No such file or directory`. Worked around by hand (`mkdir -p` the directory) to continue testing; the script itself should be fixed to create its own destination directory. **Not yet fixed in the repo — this is a real, reproducible bug on any host that never had a prior real DKMS install (e.g. any fresh reinstall), not just a one-off.**

**Hot-reload path, once the directory existed:** worked exactly as designed — unloaded the hand-`insmod`'d module (refcnt=0, clean `rmmod`), reinstalled `.ko` to disk, `depmod -a`, wrote `/etc/modprobe.d/kunlun-kl1.conf` with the requested `kl1_dma_direct=1 kl1_bounce_pipe=1`, reloaded via `modprobe` with those params, verified sha256 of disk vs. build match and all `kl1_*` parameter files present. Re-ran `tests/test_host_alloc`/`tests/test_pageable_verify` after reload — both PASS.

**Reboot survival: confirmed working.** `sudo reboot`, waited for SSH to come back (~2 min). At `uptime 0 min`, with no manual `insmod`/`modprobe`: `kunlun.ko` already loaded (`lsmod`), `/dev/xpu0`/`xpu1`/`xpuctrl` present, correct `srcversion`/`vermagic`, correct `kl1_dma_direct=1`/`kl1_bounce_pipe=1` from the modprobe.d file, clean dmesg probe (`module load success`). Re-ran the pattern tests (both PASS) and the full `xpu_perf_test` benchmark — GEMM FP16/FP32 numbers matched the pre-reboot run within noise, bandwidth reproduced the same known shortfall. **The module genuinely survives a reboot via the standard `depmod`+modprobe.d alias mechanism — this part doesn't actually need real DKMS to work, only to survive a *kernel upgrade*, which remains untested and, per the gap above, would currently fail.**

## Splitting into two install scripts: manual vs. real DKMS (2026-10-19)

Acted on the gap above by splitting the install path in two: `scripts/install_driver.sh` keeps the original hand-copy behavior (fixed, see bug below), and a new `scripts/install_driver_dkms.sh` does a real DKMS registration/build/install so the module *does* auto-rebuild on a kernel upgrade. Shared load/unload/verify logic was factored into `scripts/lib_driver_common.sh`, sourced by both. `scripts/install_ko_file.sh` got the same disk-path fix.

**Bug fixed:** `install_ko_to_disk()` (both scripts' disk-install step) did `cp -a "$KO_SRC" "$KO_DST"` with no `mkdir -p` on the destination directory first — failed on this freshly reinstalled host, which had no `/lib/modules/$(uname -r)/updates/dkms/` yet (no prior real-DKMS install had ever created it). Now creates the directory first in all three scripts.

**`install_driver_dkms.sh` design:** parses `PACKAGE_NAME`/`PACKAGE_VERSION` out of `kunlun-driver/dkms.conf` (not hardcoded, to avoid drift), stages the driver source via `git archive HEAD -- kunlun-driver` into `/usr/src/${PKG}-${VER}` (builds from the **committed** tree, like a real package would, not the working tree — commit driver changes first for this script to pick them up), removes any prior registration for that name/version, then `dkms add` → `dkms build -k $(uname -r)` → `dkms install -k $(uname -r) --force`, then reuses the same unload/reload/verify flow as the manual script.

**Retested on the R730 host (both install scripts, from the now-registered-DKMS state):**

- `install_driver.sh`: refactor is behavior-preserving — reran hot-reload, identical output to the pre-refactor run, sha256/srcversion verification and pattern tests all still pass.
- `install_driver_dkms.sh`, cold: `dkms` wasn't installed (`AUTO_INSTALL_DKMS=1` installed it via apt), staged source, `dkms add/build/install` all succeeded, `dkms status` → `installed`. Confirmed the kernel-postinst autoinstall hook is actually present and wired (`/etc/kernel/postinst.d/dkms` → `dkms_autoinstaller start`), which is what will fire on a future kernel upgrade.
- **Found and fixed a second bug in the process:** Ubuntu's `dkms install` compresses the module (`kunlun.ko.zst`), which the script's `find_ko_dst()` (exact-name `kunlun.ko` match) didn't find, and which bare `modinfo -F field <path>` can't read directly (it needs a `.ko`-suffixed path even once decompressed, or it reports "Module ... not found" and the version-mismatch check silently no-ops instead of failing loudly). Fixed `find_ko_dst()` to match `.zst`/`.xz`/`.gz` too, and added a `modinfo_file()` helper in the shared lib that decompresses to a `.ko`-suffixed temp file first.
- Pattern tests (`test_host_alloc`, `test_pageable_verify`) PASS against the DKMS-built module.
- **Reboot survival of the DKMS-built module: confirmed.** `sudo reboot`; at `uptime 0 min`, `kunlun.ko.zst` already loaded, correct srcversion/params, `dkms status` still `installed`. Re-ran pattern tests (PASS) and the full benchmark — GEMM numbers matched the non-DKMS run within noise (FP16 large 19,284 GFLOPS @ 33.48%, FP32 large 7721 GFLOPS @ 53.62%).

## DKMS kernel-upgrade survival: confirmed (2026-10-19)

Closed out the last open piece of the DKMS work: does the module actually survive a kernel **upgrade** (not just a reboot), fully automatically, via the real-DKMS registration from `install_driver_dkms.sh`?

**No genuinely newer kernel package was available** (this R730 host's `linux-generic` was already at the latest candidate, `7.0.0-38.38`). To still exercise the real mechanism faithfully, installed a *different*, already-available kernel version (`linux-image-7.0.0-14-generic` + matching headers) instead — DKMS's `dkms_autoinstaller` kernel-postinst hook fires on any new kernel package installation event, not on a version-number comparison, so this is the same trigger a genuine version bump would produce.

**The hook fired automatically during `apt install`, no manual steps:**
```

Building module(s)..................... done.
Signing module /var/lib/dkms/kunlun-module-dkms/4.33.0/build/kunlun.ko
Installing /lib/modules/7.0.0-14-generic/updates/dkms/kunlun.ko.zst
Running depmod... done.
Autoinstall on 7.0.0-14-generic succeeded for module(s) kunlun-module-dkms.
```
`dkms status` immediately showed both kernels registered (`7.0.0-14-generic: installed` alongside the original `7.0.0-38-generic: installed`) — before any reboot.

**Booted into it to confirm it's not just built but actually works.** Used `grub-reboot` for a one-time boot into `7.0.0-14-generic` (rather than changing the permanent default), rebooted:
- `uname -r` → `7.0.0-14-generic`; `kunlun.ko.zst` already loaded with no manual `insmod`/`modprobe`, correct `vermagic`/`srcversion`, clean probe.
- `tests/test_host_alloc`/`test_pageable_verify`: both PASS.
- `benchmarks/xpu_perf_test 0`: GEMM FP16/FP32 numbers matched every prior run on this host within noise (FP16 large 19,156 GFLOPS @ 33.26%, FP32 large 7727 GFLOPS @ 53.66%).

**Rebooted back to the default kernel (`7.0.0-38-generic`) to confirm the round trip didn't disturb anything there.** Came back clean: module auto-loaded, both kernel registrations still intact in `dkms status`, pattern tests PASS.

**Conclusion: real DKMS kernel-upgrade survival is fully confirmed, not just inferred from the hook being present.** `scripts/install_driver_dkms.sh` delivers exactly what it was built for — a kernel package install alone (no reboot even required to trigger the build) results in a correctly built, signed, and installed module for the new kernel, which then loads automatically and works on first boot into it. This closes the last open question from the DKMS-split work above.

## Confirmed working: driver DMA and xdnn compute are correct (2026-10-18)

An earlier hypothesis — that the untested DMA stubs above were broken — was **wrong**, and the actual bug was found and isolated:

1. **Isolated the failure to transfer, not arithmetic.** A pure round-trip through Paddle (`paddle.to_tensor(host_array).numpy()`, no math at all) came back zeroed, same as `1+1` returning `0`. This ruled out "wrong compute, right transfer."
2. **Found and fixed a real repo gap along the way:** `xdnn-ubuntu_x86_64/so/libxpuapi.so` was a Git LFS pointer (134 bytes), never fetched, in *every* clone checked (the R730 test clone and the separate local clone this `RESEARCH.md`/`CLAUDE.md` work was done from). `git lfs install && git lfs pull` fixed it (~650MB real file). Now fixed at the repo level — see "Repo/build fixes" below.
3. **Built this repo's own correctness tests** (`tests/test_host_alloc`, `tests/test_pageable_verify`) against the real XPURT library. **Both passed their pattern checks.**
4. **Ran this repo's own `benchmarks/xpu_perf_test` (full GEMM + bandwidth suite) to completion.** (It only *looked* hung under a short timeout — its stdout wasn't flushed; given the time it needs — about 1–2 minutes — it finishes cleanly, exit 0.) Results:
   - GEMM FP16: 19,151–22,597 GFLOPS at 32.96–39.23% efficiency (README's own documented baseline: ~20 TFLOPS, ~35%).
   - GEMM FP32 "large" (2048³): 7685 GFLOPS at 53.37% (documented: ~7.8 TFLOPS, ~54%).
   - INT8: correctly reports "not supported" (matches documented KL1 firmware limitation).
   - Bandwidth: real and non-zero, but **roughly half the documented peak** — pageable H2D up to 5.35 GB/s (documented ~10.1), `xpu_host_alloc` H2D up to 6.29 GB/s (documented ~12.5). This is a performance gap, not a correctness bug — flagged as open below.

**Conclusion: on this patched kernel-7.0 driver, the DMA stubs are correct and direct xdnn/XPURT compute matches the repo's own documented numbers.** The `README.md` and `docs/BUILD-linux-7.md` "Stubs" language has been updated from "untested guesses" to "confirmed correct" accordingly. **Caveat added 2026-10-19:** `xpu_perf_test`'s GEMM numbers are a *timing/throughput* match (GFLOPS at the expected efficiency for this card), not a value-level check — it never compares output against a reference. That's reasonable circumstantial evidence real compute is happening (a broken/no-op kernel wouldn't consume the expected amount of time), but it isn't the same as checking the actual numbers. The first direct value-level check of `xdnn::fc()` against a CPU reference happened during the BERT/ERNIE attention work below — exact match, genuinely confirming correctness, not just plausible timing.

## Confirmed broken: the official `paddlepaddle-xpu` wheel (2026-10-18)

With the driver above loaded and working (confirmed by the tests in the previous section), the official pip wheel still fails at the compute level:

- Installed via `pip install https://paddle-whl.bj.bcebos.com/paddlex/xpu/paddlepaddle_xpu-2.6.1-cp310-cp310-linux_x86_64.whl` (needs Python 3.10 — see "Getting Python 3.10" below; no official index URL found for 2.6.1, only this direct wheel link, via PaddleX's Kunlun XPU docs).
- `paddle.is_compiled_with_xpu()` → True, `paddle.device.xpu.device_count()` → 2 (matches the two `/dev/xpu*` nodes), `paddle.set_device("xpu:0")` succeeds. Detection works fine.
- But: `paddle.to_tensor(host_array).numpy()` returns all zeros (silent data loss, no exception); elementwise add and matmul of all-ones tensors also return all zeros; `paddle.randn(...)` raises `OSError: ... XDNN Error, XDNN_INVALID_PARAM`.
- **Root cause, isolated:** Paddle's wheel bundles its own `libxpuapi.so` (587MB, version string `XDNN_VERSION_master-changed`, build workspace paths reference newer kernel source such as `xpu/refactor/page_attention.h` that doesn't exist in this repo's own bundled copy). This repo's bundled `libxpuapi.so` is a *different build* (650MB) and is proven correct (previous section). The kernel module is not the cause. **Correction, 2026-10-19:** the XPURT transfer layer was originally described here as "shared/identical" between the two scenarios — that was wrong. Both report the same nominal version string (`XRE_4.31.0`), but different git commit hashes (`9961634a...` in this repo's copy vs. `166f4877...` in the wheel's) — different builds, like `libxpuapi.so`. This didn't end up mattering (see below: the wheel's bundled XPURT, tested directly, works correctly), but the original claim of identity was incorrect and is corrected here.
- **Corroborating public report:** [PaddlePaddle/Paddle#56781](https://github.com/PaddlePaddle/Paddle/issues/56781) — a different user reported Paddle release/2.5 "compiled but hung at runtime" on K200 (different symptom, same underlying story: Baidu's official Paddle builds don't reliably run compute correctly on K200, even when they load and detect the device). A community reply in that thread claims Paddle versions after 2.3 dropped K200 support outright; this is **unconfirmed** — no official release note was found, and the thread's actual evidence is messier (a 2.2 build failed only because Baidu's CDN URLs for the XRE/XDNN tarballs had expired, an infrastructure problem, not a version gate).

### Update 2026-10-19: tried the fix, failed (ABI incompatible) — and the bug is narrower and worse than "returns zero"

Reinstalled the wheel fresh on the just-reinstalled R730 host (Python 3.10.14 via pyenv again, since the OS reinstall wiped the earlier venv) and retested before touching anything:

**Attempted fix: point Paddle at this repo's own, proven-correct `libxpuapi.so`.** Confirmed via `readelf -d` that Paddle's `.so`s use `RUNPATH` (not `RPATH`), so `LD_LIBRARY_PATH` *should* take precedence — tried `LD_LIBRARY_PATH=.../xdnn-ubuntu_x86_64/so python3 -c "import paddle"` and it failed immediately at import: `undefined symbol: _ZN5baidu3xpu3api15layer_norm_gradIffEEi...`. Confirmed via `nm -D | c++filt` that this repo's `libxpuapi.so` does export `layer_norm_grad<float,float>`, but with a **different parameter list** than the mangled symbol Paddle's `libphi.so` was built against — the two builds are genuinely ABI-incompatible, not just "different builds of the same API." **Replacing the wheel's bundled file outright would hit the identical failure** (same library content, same missing symbol), so both halves of this TODO item's approach are dead ends as stated. This closes the question the previous entry left open.

**The actual bug, re-characterized (more precise and more concerning than "returns zero"):** earlier testing only ever saw zeros, which happened to look like clean silent data loss. Retesting with non-trivial data shows it isn't a zero-fill at all:
- `paddle.ones([4,4])` + `paddle.uniform(...)`, add, and matmul **all produce numerically correct results** — on-device compute itself is fine.
- `paddle.to_tensor(host_numpy_array).numpy()` does **not** reproduce the host data, doesn't even reliably return zero, and the pattern scales with how much device memory has already been touched this process: a 4×4 host array came back with only the first row populated (and that row's values didn't match the input either — they matched an *unrelated earlier tensor's* values) and the rest zero; a 1024-element array came back with only 4 nonzero elements, again matching stale data from a previous allocation.
- **Proved it directly:** allocated a `[6]` tensor filled with `999.0`, read it to force materialization, freed it. Immediately called `paddle.to_tensor([1,2,3,4,5,6])` (same size). Result: `[999, 999, 999, 999, 999, 999]` — the new tensor reused the just-freed device memory block, and **the host→device copy never happened at all**; it's reading back stale content from a previous, unrelated allocation.
- **Conclusion: this is not "compute returns zero," it's "the H2D copy backing `paddle.to_tensor()` from a host array is a silent no-op."** Device-side compute (arithmetic, matmul, on-device random generation) and this repo's own driver DMA (already proven correct via `tests/test_host_alloc`/`tests/test_pageable_verify`) are both unaffected. The bug is isolated to whatever code path Paddle's own framework (not necessarily `libxpuapi.so`/`libxpurt.so` — could be `libphi.so`/`libpaddle.so`'s own tensor-copy glue) uses to stage a numpy array onto an XPU place. Not yet isolated further — that's the next step if this is revisited.

**Bonus finding answering the *other* open TODO item** ("does the wheel's own bundled `libxpuapi.so` have `xpu1::` LLM kernels this repo's copy lacks?"): **yes, partially.** `nm -D | c++filt` on the wheel's bundled copy shows `rotary_embedding`/`rotary_embedding_v2`/`v3`/`_bhld`, `swiglu`/`fast_swiglu`, `rms_layer_norm`, and `qkv_paged_attention` all present as **flat, non-namespaced** symbols (this repo's own heuristic for "xpu1-candidate") — a real difference from this repo's copy, where every one of these is gated to `xpu2::`/`xpu3::` only. The wheel's library (587MB) is evidently a materially different/newer SDK build with broader kernel coverage.
- **But it doesn't actually help:** tested Paddle's own `fused_rotary_position_embedding` op (the building block PaddleNLP's llama2 implementation uses) directly against `xpu:0` with a toy tensor. Result: `RuntimeError (NotFound): The kernel with key (XPU, ..., float16) of kernel 'fused_rotary_position_embedding' is not found`. **Paddle's own PHI kernel registry has no XPU backend registered for this op in the 2.6.1 wheel at all**, regardless of what raw symbols exist in `libxpuapi.so` underneath. This is a higher-level gate than the xdnn symbol table — the kernel *could* theoretically exist and dispatch correctly on this silicon, but Paddle 2.6.1 never wired an XPU code path to call it. This is a hardware/software-confirmed (not just static-analysis) answer to the llama2-7b feasibility question for this specific wheel version: it's a dead end as shipped, independent of the xdnn-level kernel-availability question. Downloading and running the full PaddleNLP llama2-7b tutorial was not attempted given this result makes the outcome foregone at the very first fused op it would hit.

### Update 2026-10-19 (continued): bug fully isolated to Paddle's own framework glue — driver, XPURT, and XDNN all cleared

Followed the TODO item through to isolate exactly which software layer the `to_tensor()` no-op lives in, working from the lowest layer up:

1. **Tried call-tracing it directly** with an `LD_PRELOAD` shim intercepting `xpu_memcpy`/`xpu_memcpy_ex` (dlsym/`RTLD_NEXT`, forwarding to the real symbol). Logged exactly one call — a 64-byte D2H copy during XPU context init — then **segfaulted inside the real call itself**, reproducibly, with or without raising glibc's static-TLS reserve (`GLIBC_TUNABLES=glibc.rtld.optional_static_tls=...`, a known class of fix for this kind of crash). Not pursued further — logged here as a real anomaly (interposing this specific symbol in this specific process is fragile) but abandoned in favor of a safer isolation method below, since it wasn't the goal in itself.
2. **Bypassed Paddle entirely and called the wheel's own bundled `libxpurt.so.1` directly via `ctypes`**: `xpu_set_device(0)` → `xpu_malloc` → `xpu_memcpy(H2D)` → `xpu_wait` → `xpu_memcpy(D2H)`, no Paddle tensor machinery involved at all. **All four calls returned 0, and the round-tripped data matched exactly** (`[1..8]` in, `[1..8]` out). This conclusively proves the wheel's bundled XPURT — despite being a different build from this repo's own (see correction above) — correctly performs H2D/D2H transfers against this card's driver. The bug is not in XPURT.
3. **Confirmed on-device compute is unaffected** (already shown above): `paddle.ones`/`uniform`, add, matmul all produce correct results using the wheel's own `libxpuapi.so`. The bug is not in XDNN/`libxpuapi.so` either.
4. **Narrowed further: it's not XPU-specific at all.** Requesting `place=paddle.CPUPlace()` explicitly, or running in a fresh process with no `paddle.set_device()` call whatsoever, **still produces garbage** on `to_tensor(host_array)` — e.g. `[10,20,30,40]` in, `[-7.9e+37, -3.16e+38, 5.33e-38, 5.29e-38]` out. (Also discovered along the way: this `paddlepaddle-xpu` wheel defaults the global device to `xpu:0` even with no explicit `set_device` call — `t.place` reports `Place(xpu:0)` by default.) The failure is in Paddle's own host-array-ingestion path for `to_tensor()`, not anything XPU-device-specific about it.

**Conclusion: the bug is now isolated as far as reasonably possible without building Paddle from source.** Driver, XPURT, and XDNN compute are all independently proven correct in this exact environment. The fault lives entirely in Paddle's own framework code — the `to_tensor()`/tensor-construction-from-numpy glue (`libphi.so`/`libpaddle.so`), not the XPU-specific layers underneath it. The garbage-not-zero symptom (reading back unrelated memory content) is consistent with a copy that's skipped or misdirected rather than one that executes with wrong data. Pinning the exact C++ function/line responsible would need Paddle built from source with debug symbols — a materially bigger undertaking, now clearly scoped as the next step if this is picked up again (see `TODO.md`).

### Update 2026-10-19 (continued further): exact bug found via live `gdb`, no Paddle rebuild needed

Turned out a from-source rebuild wasn't necessary: `libpaddle.so` ships with **full, unstripped DWARF debug info** (`.debug_info`/`.debug_line`/etc., confirmed via `readelf -S`) and ~320K symbols. Installed `gdb` and traced the live call chain directly against the installed wheel, cross-referencing hit addresses against the public `PaddlePaddle/Paddle` `v2.6.1` tag (shallow `--filter=blob:none` clone) for context — while confirming empirically that this wheel's actual compiled logic diverges from that public tag in places, so the tag was used as a map, not assumed to be the literal shipped source.

**Call chain walked, each link confirmed by a real breakpoint hit (not inferred):**
`TensorInit` → `AutoInitTensorByPyArray` → `InitTensorWithNumpyValue` (the `(TensorObject*, array, place, zero_copy)` overload — disambiguated from a same-named, differently-signatured overload in `eager_math_op_patch.cc` via breakpoint `info breakpoints` showing two resolved locations, `1.1`/`1.2`) → `SetTensorFromPyArrayT<float, phi::XPUPlace>` (located via `info functions` once the library was loaded, since GDB won't pending-resolve a breakpoint by name on this specific non-debugging/template symbol — had to compute its live address from a known-working symbol's live-vs-static offset "slide" and `break *ADDRESS`) → `paddle::memory::Copy<phi::Place, phi::CPUPlace>` → `paddle::memory::Copy<phi::Place, phi::Place>` (the actual runtime AllocationType dispatcher).

**Verified empirically, at the dispatcher, that routing is correct up to the last step:** `dst_place.GetType() == 4` (`AllocationType::XPU`, confirmed against `paddle/phi/common/place.h`'s enum) and `src_place.GetType() == 1` (`CPU`) — both read directly from registers at the exact `cmp`/`je` instructions — correctly select the "CPU→XPU" branch (disassembly offset `+952` within the dispatcher).

**The bug: inside that correctly-selected branch, the binary does something unexpected.** Instead of directly constructing an `XPUPlace` and calling `Copy<XPUPlace, CPUPlace>` (the public source's own documented path, which calls `platform::MemcpySyncH2D` — confirmed via a live breakpoint on that exact symbol that it is in fact **never** called across the whole process, despite resolving to a real, non-pending address), the compiled code first calls into `phi::CustomRegisteredDeviceMap` (Paddle's generic **CustomDevice plugin** device-type-string registry — not anything XPU-native), then constructs a **new `phi::Place` with `AllocationType::CPU`** (not XPU — confirmed live: `mov esi, 0x1` immediately before the `phi::Place` constructor call), and finally calls **`paddle::memory::Copy<phi::CPUPlace, phi::XPUPlace>`** — the **D2H-shaped overload** (internally calls `MemcpySyncD2H`, confirmed in the public source), from inside the branch meant to handle H2D. Confirmed live at that exact call site: the "dst" argument slot held a host-looking address, the "src" slot held a device address matching this session's known XPU allocation pattern, and the size argument was `0x400` (1024 bytes) — not this test's actual 24-byte array — consistent with a stale/garbage or unrelated size, not the intended copy's real length.

**Conclusion:** this specific `paddlepaddle-xpu` 2.6.1 wheel's compiled `Copy<phi::Place, phi::Place>` runtime dispatcher has a genuine bug in its CPU→XPU (H2D) branch — it calls the opposite-direction (`CPUPlace, XPUPlace`, i.e. D2H) overload instead of the needed one, via code that routes through Paddle's generic CustomDevice plugin machinery rather than native XPU place construction (this wheel evidently implements at least part of its XPU support through that more generic mechanism, which is **not** how the public, vanilla `PaddlePaddle/Paddle` source at this tag does it — confirming this wheel's actual source is a Baidu-internal variant, not a straight build of the public tag). This fully explains every observed symptom: no H2D `xpu_memcpy` ever issued, the device buffer is never actually written, and reads return whatever was already there. Fixing it would require Baidu's own (non-public) source for this wheel — out of reach from outside that channel, same caveat as the "newer driver" open question elsewhere in this file. This is as far as isolation can go without that source.

## Ollama / vLLM feasibility: static analysis (2026-10-18, no hardware access — machine off)

Investigated whether either is realistically achievable on K200, without assuming "no official support" is the whole story.

**Confirmed via web search: neither has any existing path.**

- vLLM: Baidu's own `vllm-kunlun` plugin supports Kunlun3 (P800) only and runs on `xpytorch`, a KL3-customized PyTorch build distributed as a `.run` installer; nothing comparable exists for KL1. (Already established pre-2026-10-18, re-confirmed here.)
- Ollama: it runs on `llama.cpp`/`ggml`. No Kunlun backend of any kind was found in ggml, upstream or third-party — `llama.cpp`'s backend list (CUDA, HIP, Metal, Vulkan, MUSA, SYCL) doesn't mention Kunlun, and no PR/issue proposing one turned up. Baidu's own Kunlun investment is in Paddle and vLLM, not llama.cpp.
- PaddleNLP (Baidu's own LLM-serving path, the closest thing to "does any transformer model run on Kunlun hardware via Baidu's own tooling") targets **Kunlun2 (R300/R480, driver 4.31.0)** for its documented llama2-7b tutorial — not K100/K200. This matches the finding below.

**New finding, from inspecting this repo's own `libxpuapi.so` directly (no card needed — `nm -D`/`strings` on the 650MB file already in this checkout):**

The library's compute kernels are namespaced by hardware generation: `xpu2::` (~15,700 functions), `xpu3::` (~8,000), `xpu4::` (~245) — presumably Kunlun2/3/4. **Zero symbols exist in an `xpu1::` namespace** (K100/K200's architecture). Every transformer-serving primitive checked — `rotary_pos_embedding`/RoPE, `swiglu_fwd`/`swiglu_bwd`, `rms_layer_norm_infer` (RMSNorm), `qkv_paged_attention` — exists only under `xpu2::`/`xpu3::`.

K100/K200 (xpu1) code does exist in the same library, but only for older-generation ops, as flat (non-namespaced) C functions: GEMM/FC/conv (matches this repo's own working GEMM benchmarks) and `XPU1ActTable`, whose lookup tables cover `relu`/`sigmoid`/`tanh`/`gelu`/`swish`/`hard_sigmoid`/`hard_swish` — i.e. CNN- and BERT-era activations, with **no SwiGLU and no RMSNorm table**. This lines up with what K200 was actually built and validated for in this repo (ResNet-50, BERT-style fixed-size attention), not LLaMA-family decoder architectures.

**Reading:** this isn't a driver-version or packaging gap like the `paddlepaddle-xpu` silent-zero bug (open question above) — the low-level kernels current LLM serving needs appear to have never been written for KL1 silicon in Baidu's xdnn library, at least not in the build bundled in this repo. Not yet checked: whether the *Paddle wheel's own* bundled `libxpuapi.so` (587MB, a different build) has any `xpu1::` LLM kernels this repo's copy lacks — a cheap `nm -D` check, but it needs the R730 host where that wheel is installed, not this machine.

**Plan of attack, ranked by cost and what each step would actually prove:**

1. **Cheapest next step, on the R730 (combine with the already-planned `LD_LIBRARY_PATH` fix above):** once the `paddlepaddle-xpu` wheel is pointed at this repo's proven-correct `libxpuapi.so`, try running PaddleNLP's own XPU llama2-7b tutorial against K200 and capture the real failure. This turns the binary-analysis hypothesis above into a hardware-confirmed fact (or disproves it) for near-zero extra cost, since the environment would already be set up for the wheel fix.
2. **Cheap, no hardware needed:** `nm -D`/`c++filt` the Paddle wheel's own bundled `libxpuapi.so` for `xpu1::` RoPE/SwiGLU/RMSNorm/paged-attention symbols — confirms whether this repo's copy is simply missing kernels a newer build has, before concluding they're absent for KL1 everywhere.
3. **If (1)/(2) confirm the kernels genuinely don't exist for xpu1:** a custom `llama.cpp`/ggml backend calling into xdnn directly is *conceivable* (xdnn's kernels are written against the `xpu/kernel/cluster*.h` SIMD/cluster-primitive headers bundled in this repo, so the programming model is visible), but would mean hand-writing RMSNorm/RoPE/SwiGLU/attention device kernels from scratch against those primitives and compiling them with Baidu's XTDK device compiler. **Update 2026-10-19: XTDK is confirmed publicly obtainable** (see "XTDK device compiler" below) — the compiler-availability gate is cleared, but the hand-written-kernel engineering work itself is still untouched and substantial. Even in the best case, K200's firmware has no INT8 CDNN kernel (already confirmed above), so the result would be FP16-only — no GGUF-style quantization, limiting it to small models fitting 8GB HBM/XPU in FP16.
4. **vLLM: not worth independent effort.** It would need a from-scratch equivalent of `xpytorch` (full PyTorch device backend: ATen op coverage, autograd, etc.) sitting on top of the same missing kernel layer found in (3) — strictly more work than (3) for the same underlying gap, with no indication Baidu plans to ship `xpytorch` for KL1.

## Other workloads this card's actual kernel set fits (2026-10-18, same static analysis)

While checking `libxpuapi.so` for LLM kernels (previous section), also checked what *is* present for xpu1 (K100/K200), beyond the GEMM/conv/activation ops already confirmed by this repo's own benchmarks. Ranked by how directly the evidence supports each:

- **K-means clustering — confirmed working end to end on real hardware, not just a static-analysis guess.** The whole algorithm maps onto primitives that are flat/non-namespaced (so xpu1-available) with nothing gated to `xpu2::`/`xpu3::`: distance-to-centroids is `‖x‖² + ‖c‖² - 2x·cᵀ` (GEMM, already proven, plus `square`/`reduce_sum`); assignment is `argmin` over the distance row; and the centroid update — normally a group-by-sum, the same shape that blocks GNN message passing — sidesteps that entirely via the standard trick of building a one-hot assignment matrix (`one_hot`) and computing per-cluster sums as a single GEMM (`one-hotᵀ @ X`) with counts via `reduce_sum`. **Update 2026-10-19: tested directly, a full iteration wired together in one program, exact bit-match to hand-computed expectations, device left fully healthy — see "K-means clustering: confirmed working end to end" below.** Caveat (unchanged by the test): it's an iterative distance→assign→update loop, several kernel launches per pass, fine for batch clustering, not for sub-millisecond online use.
- **Recommendation / ranking / CTR-style models — looks like this card's original intended workload.** Non-namespaced (so presumably xpu1-available) symbols include `search_grnn`/`search_bi_grnn`/`search_grnn_pointer_max` (Baidu's GRNN cell, used in its search/ads ranking stack), `search_seq_softmax`/`multi_softmax`, embedding `gather`/`gather_nd`/`scatter_assign`, and `baidu::xpu::api::random<T>` (on-device Philox-backed RNG, useful for dropout/init/sampling). Together these are the building blocks of a classic GRNN/MLP/embedding CTR or learning-to-rank model (DSSM/Wide&Deep/DIN-style), which predates LLaMA-era transformers and matches when this chip generation shipped. **Update 2026-10-19: tested directly on real hardware — the documented public API (`baidu::xpu::api::grnn_cell`, not the raw `search_grnn*` symbols, which have no header declaration and aren't meant for direct use) triggers a genuine hardware-level exception on dispatch, not a clean rejection.** See "`grnn_cell`: undocumented calling convention found, then a real hardware exception" below.
- **Classic CNN vision, beyond ResNet-50/denoise already proven.** `batchnorm_fwd_infer`/`_train`/`_bwd`, `pooling_fwd`, `avg_pooling_backward`, `max_pooling_backward`, and `conv2d_fusion` all present without generation-specific namespacing, and `conv2d_fusion` is already proven working on real hardware (this repo's own `xpu_denoise` benchmark uses it directly). Object detection or segmentation models built from these primitives (hand-composed conv+BN+activation, the way `xpu_denoise` already does it) should fit the same envelope. **Update 2026-10-19: the `fusion_cv.h` convenience wrappers specifically — `resnet_unit_fusion` and `yolo_unit_fusion` — do not work on xpu1, tested directly; see "`*_unit_fusion` convenience wrappers: confirmed broken on xpu1" below.** Nothing currently in this repo exercises these two specific functions (the proven ResNet-50/denoise cases use plain `conv2d_fusion` + separate ops, not the fused "unit" wrappers), so this doesn't contradict anything already working — it rules out a shortcut, not the underlying primitives.
  - **OpenCV: no native path, but a standard hybrid pipeline works.** OpenCV has no Kunlun/XPU backend, and its one vendor-agnostic GPU route (the T-API/`UMat` OpenCL path) needs an OpenCL ICD this card doesn't have — checked `libxpurt.so.1` for `cl*` entry points, none exist. There's also no on-device image-decode/resize in this SDK (no JPEG/codec headers under `xdnn-ubuntu_x86_64`), unlike some vendor SDKs. The realistic pattern is the usual GPU-inference split: OpenCV on the CPU for capture/decode/resize/color-convert/drawing, `xpu_memcpy` the preprocessed tensor across, run conv/pooling/batchnorm/`yolo_unit_fusion` inference on the card via xdnn, copy the result back for OpenCV to draw. Nothing in this repo uses OpenCV today (not referenced anywhere, not installed on this dev machine) — this would be new integration work, but the same shape as the existing `benchmarks/`/`tests/` code (direct `xpu_memcpy` + xdnn calls), not a new kind of problem.
- **Classic (non-VL) OCR inference — conv, softmax, and both the unidirectional and bidirectional recurrent layer are now confirmed; only scale remains open.** CRNN-style detection/recognition is conv backbone + recurrent layer (standard CRNN, including PaddleOCR's own, uses bidirectional LSTM here, not GRNN) + softmax decode. Conv (`conv2d_fusion`) and softmax are genuinely confirmed working elsewhere in this doc. **Update 2026-10-19: both `lstm_inference` and `bilstm_inference` tested directly on real hardware and confirmed working, not another `grnn_cell` — see "`lstm_inference`: confirmed working" below**, including the follow-up there confirming `bilstm_inference<float,float,short>` too (dispatches genuinely on `api::kXPU1` via real `bilstm_train`/concat machinery, correct-range reproducible output, device left fully healthy, re-verified against the established GEMM baseline) — categorically different from `grnn_cell`'s outcome despite all three being untested `fusion.h` recurrent-cell APIs beforehand. Still open: whether this scales cleanly to realistic (larger, batched) CRNN dimensions rather than the toy shapes used in both tests. CTC-loss *training* (`ctc_loss_bwd`/`ctc_cost_grad`) is still confirmed `xpu2::`/`xpu3::`-only regardless, so a new CTC model can't be trained here either way; inference-time decode (greedy/beam over softmax output) needs no CTC kernel and isn't affected by any of the above. **Net: upgraded all the way to "looks feasible" — every kernel a pretrained CRNN inference pipeline needs is now individually confirmed correct and safe on xpu1; the only remaining step is assembling and running a real model at realistic scale end to end, which hasn't been done.**
- **BERT/ERNIE-era encoder models (pre-LLaMA transformers) — confirmed working.** The plain (non-RMS) `baidu::xpu::api::layer_norm<T>` wrapper and `XPU1ActTable::get_gelu_table` both exist without generation gating, and GEMM+softmax (both confirmed working) are enough to hand-compose unfused multi-head attention the way pre-2023 model code did, instead of calling the xpu2/3-only fused `attention.h`/`page_attention.h` kernels. **Update 2026-10-19: tested directly on real hardware and confirmed numerically correct — see "Hand-composed BERT/ERNIE-style attention: confirmed correct on real hardware" below.**
- **Graph neural networks — weak fit, likely blocked.** GNN message passing needs scatter-add/segment-sum (aggregating a variable number of neighbor features per node) or sparse matmul (SpMM) as its core primitive. `index_add` (the actual scatter-add kernel) exists only under `xpu2::`/`xpu3::`, same generation-gating as the LLM ops, and there's no `segment_sum`/SpMM/CSR support anywhere in this xdnn SDK regardless of generation. What's ungated — generic `gather`/`gather_nd`/`scatter_assign` (`assign`, not `add`, so no built-in accumulation), and `sparse_adam`/`sparse_sgd` (sparse-gradient optimizers for embedding tables, not graph aggregation) — isn't enough to build real message passing on. Baidu's own GNN framework, PGL, is built on Paddle but nothing in its docs claims Kunlun-kernel support, and it would need the same missing scatter-add primitive. A GNN layer here would mean hand-writing a scatter-add/segment-sum kernel against the raw cluster-primitive headers — needs the same XTDK compiler as the custom ggml-backend path above, **now confirmed publicly obtainable** (see below), so this is no longer blocked on compiler availability, only on the kernel-writing effort itself.
- **Bare compute/RNG coprocessor, bypassing any ML framework entirely.** This is what this repo's own benchmarks and tests already do (direct xdnn/XPURT GEMM calls), and it's the lowest-risk way to use the card for anything: batched FP16/FP32 matrix math, image/signal processing (the existing denoise case), or Monte Carlo-style workloads using the on-device RNG — no dependency on any serving stack's device-generation gating at all.

## Image segmentation ops: two confirmed working, two confirmed unimplemented (2026-10-20)

Follow-up to the "Image segmentation" item in "Further investigation" above. All four ops (`interpolate2d`, `conv2d_transpose`, `roi_align`, `roi_pool`) were first confirmed as concrete `<float>`/`<float,int>` instantiations in `libxpuapi.so` with `nm -D --defined-only | c++filt` (same check as every other op in this doc), then tested directly on the real K200. Device health (`tqinfo`, all 8 queues) was checked before and after every test, and a full `xpu_perf_test 0` GEMM+bandwidth run (about 2 minutes) was done afterward — all queues stayed `NORMAL` throughout, `#all=0`/`#running=0`. Full test sources: [example 10](docs/research/20261019-xpu1-op-testing-examples.md#10-image-segmentation-ops-interpolate2d-conv2d_transpose-roi_align-roi_pool--two-confirmed-working-two-confirmed-unimplemented).

**`interpolate2d<float>` — confirmed working.** A 1×1×2×2 image `[[1,2],[3,4]]`, nearest-neighbor-upsampled 2× to 4×4, gave exactly `[[1,1,2,2],[1,1,2,2],[3,3,4,4],[3,3,4,4]]` — the hand-computed expectation with no ambiguity. `ret=0`, reproducible across two runs.

**`roi_align<float,int>` — confirmed working, but with a non-obvious convention.** Used a 4×4 linear-ramp image (`value = 4*row+col`, chosen because bilinear interpolation of a linear function is exact regardless of exact sample-point placement) with a single ROI `(0,0,4,4)` covering the whole image, `spatial_scale=1.0`, `sampling_ratio=1`, `mode=0` (avg), pooled to 2×2. First attempt assumed the "aligned" convention used by PyTorch/Detectron2 (bin centers offset by `-0.5` before interpolating), predicting `[2.5, 4.5, 10.5, 12.5]`; the actual result was `[5, 7, 13, 15]`, a clean mismatch. Re-deriving under a legacy (non-aligned) convention — bin centers mapped directly to integer pixel-index coordinates, no half-pixel offset — predicts exactly `[5, 7, 13, 15]` (each bin's sample lands precisely on an input pixel, e.g. bin `(0,0)`'s center falls on pixel `(row=1,col=1)=4*1+1=5`), which matched. **Anyone porting a model's RoIAlign here must account for this**, not assume "aligned=True" semantics transfer unchanged.

**`conv2d_transpose<float,float,float,float>` — confirmed unimplemented.** A minimal deconvolution (1×1×2×2 input, 1-in/1-out-channel all-ones 2×2 kernel, stride 1, no padding, expected 3×3 "scatter-add" output `[[1,3,2],[4,10,6],[3,7,4]]`) returned `ret=4` immediately, with an explicit `[XDNN_UNIMPLEMENTED][src/wrapper/nn_conv2d_transpose.cpp:119]` trace line under `XPUAPI_DEBUG=1` — a clean rejection from Baidu's own wrapper code, not a hardware fault or hang. Device stayed healthy.

**`roi_pool<float,int>` — confirmed unimplemented.** Same setup as the `roi_align` test above (ROI covering the whole 4×4 ramp image, 2×2 output, max-pool semantics chosen to be convention-independent on a monotonic ramp). Returned `ret=4`, same `XDNN_UNIMPLEMENTED` signature, device stayed healthy.

**Conclusion:** a decoder path built from `interpolate2d` + `roi_align` alone is the realistic feasible subset on this card; `conv2d_transpose` (U-Net-style deconvolution) and `roi_pool` (Mask R-CNN-style RoI max-pooling) are not available regardless of model architecture chosen. Still untested: `interpolate1d` (same family, not retested given `interpolate2d`'s clean pass), `interpolate2d`'s bilinear mode and other `trans_mode` values, FP16 instantiations, multi-ROI/multi-image batches, and `ps_roi_align`/`ps_roi_pool` (not checked at all).

## NCF-style recommendation: confirmed working on real hardware (2026-10-20)

Follow-up to the "NCF-style recommendation" item in "Further investigation" above — the credible alternative to the CTR/ranking row's `grnn_cell` hardware exception, since NCF needs no recurrent cell at all. `gather<float,int>`, `fc<float,float,float,float>`, and `sigmoid<float>` were each confirmed as concrete xpu1 instantiations with `nm -D --defined-only | c++filt` first (same check as every op in this doc), then wired into a full minimal forward pass. Full test source: [example 11](docs/research/20261019-xpu1-op-testing-examples.md#11-ncf-style-recommendation-gather--fc--sigmoid--confirmed-working).

**Setup:** a 2-user × 2-dim embedding table `[[1,2],[3,4]]` and a 2-item × 2-dim embedding table `[[5,6],[7,8]]`. `gather(..., axis=0)` looked up user_id=1 (→ `[3,4]`) and item_id=0 (→ `[5,6]`), writing directly into adjacent halves of a single 4-element device buffer (no separate concat kernel needed — just pointing each gather's output at the right offset). Reproducible across two runs; `tqinfo` showed all 8 queues `NORMAL` both before and after, with no GEMM-suite regression.

**Conclusion:** this architecture is a viable recommendation-model path on this card, confirmed end to end at toy scale, and specifically avoids the one op (`grnn_cell`) with a documented (if no-longer-reproducible) hardware-exception history. Still untested: realistic embedding-table and batch sizes, and multi-layer MLP towers (only a single `fc` layer was tested).

## Hand-composed BERT/ERNIE-style attention: confirmed correct on real hardware (2026-10-19)

Followed up on "BERT/ERNIE-era encoder inference (hand-composed, unfused attention)" with a real test — and this one is a clean positive result, unlike the `*_unit_fusion`/`grnn_cell` investigations above. Full, reusable example source: [`docs/research/20261019-xpu1-op-testing-examples.md`](docs/research/20261019-xpu1-op-testing-examples.md#1-hand-composed-berternie-style-attention--working-example).

**Built a minimal single-head self-attention block entirely from individually-proven primitives**, exactly the way pre-fused-kernel-era model code did it: `fc` for the Q/K/V and output projections, `fc` (with `w_trans=true`) + `scale` + `softmax` for scaled dot-product attention, `add` for the residual connection, and `layer_norm` for the final normalization. No `attention.h`/`page_attention.h` fused kernels (confirmed elsewhere to be `xpu2::`/`xpu3::`-only) anywhere in the pipeline.

**First attempt produced nonsensical, astronomically large output** (values like `3.3×10^16`) at the very first `fc(Q)` call, which triggered a careful debugging detour — important to document since it could easily be mistaken for a real hardware/driver finding:
- Initially suspected `fc<float,...>` silently required real `x_maxptr`/`w_maxptr` scale buffers rather than `nullptr` (unlike `conv2d_fusion`'s proven nullptr-is-fine convention in `xpu_denoise.cpp`) — added explicit `findmax` calls to compute real scale buffers. No change.
- Suspected a stream mismatch between `xpu_wait()` and `Context`'s own `xpu_stream` — checked, `ctx->xpu_stream` is `nullptr` (the same default stream), ruled out.
- Suspected `xpu_set_device(0)` was missing before `xdnn::create_context()` (every working call in `xpu_perf_test.cpp` does this; my test didn't) — added it. No change.
- **Noticed `xpu_perf_test.cpp` never actually checks GEMM output values, only timing/GFLOPS** — raising a real concern that `fc()`'s numerical correctness might never have been verified in this repo at all, only its throughput. Wrote an isolated, minimal `fc()` test (4×4×4, all-ones inputs, hand-computed expected output) — **passed, exact match.** Then the same isolated test at realistic 64×64×64 scale with the attention test's actual weight-initialization pattern, checked against a CPU reference — **failed, with the CPU reference *also* producing the same huge garbage values.**
- **Root cause, finally found: a bug in the test's own code, not in `fc()`, the driver, or the hardware.** The weight-initialization loop used `for (size_t i = ...) w[i] = 0.02f * (float)((i*3) % 5 - 2)` — with `i` as `size_t` (unsigned), `(i*3)%5 - 2` underflows to a huge unsigned 64-bit value whenever the modulo result is 0 or 1, which then casts to an enormous float (~10^19). Fixed by making the loop variable `int64_t` (signed); the isolated test immediately matched the CPU reference bit-exactly, and the full attention pipeline then produced correct values at every stage.

**With that fixed, the full pipeline is confirmed numerically correct end to end**: Q values in the expected small range, attention scores and softmax probabilities exactly matching hand-calculable expectations (near-uniform scores → probabilities ≈ 1/64 for a 64-length sequence, bang on), and final `layer_norm` output properly normalized into the expected range. No `dmesg` warnings or hardware exceptions at any point.

**Conclusion: BERT/ERNIE-era encoder inference via hand-composed, unfused attention is confirmed working and numerically correct on K100/K200.** This is the first of this session's three deeper workload investigations (`*_unit_fusion`, `grnn_cell`, this one) to come back clean — worth noting as a useful calibration: not everything "flat/non-namespaced" on this card is broken or dangerous, and the debugging process above is a useful cautionary tale about checking your own test harness (especially unsigned-arithmetic loop variables) before concluding a hardware/driver/library issue — `xpu_perf_test.cpp`'s established "GFLOPS looks right" standard does *not* by itself prove GEMM numerical correctness, only that *something* resembling a real compute-bound kernel ran; this is the first direct numerical verification of `fc()` against a CPU reference in this repo's own work.

## `grnn_cell`: undocumented calling convention found, then a real hardware exception (2026-10-19)

Followed up on "CTR / ranking / recommendation (GRNN/DSSM/Wide&Deep-style)" from the static analysis above with a real test of `baidu::xpu::api::grnn_cell` — the actual public, header-declared API for Baidu's GRNN cell (the raw `search_grnn`/`search_bi_grnn`/`search_grnn_pointer_max` symbols found by the earlier static analysis have no header declaration anywhere in this SDK and aren't meant to be called directly; `grnn_cell` in `xpu/refactor/fusion.h` is the real entry point). Full test source (reverse-engineered calling convention, with the hardware-exception warning): [`docs/research/20261019-xpu1-op-testing-examples.md`](docs/research/20261019-xpu1-op-testing-examples.md#3-grnn_cell--correct-calling-convention-then-a-real-hardware-exception).

**No public example or gtest ships with this SDK for `grnn_cell`**, so its exact calling convention had to be reverse-engineered through iterative testing, using `XPUAPI_DEBUG=1` (an undocumented but real env var, found via `strings` on `libxpuapi.so`) to see why each attempt failed:

1. First attempt (2 weight matrices, non-null `h_prev`, separately `xpu_malloc`'d buffers): `[ASSERT-FAIL](ptr(...)==nullptr)` — `h_prev` must be `nullptr`.
2. With `h_prev=nullptr`: `[ASSERT-FAIL](2==3)` — GRNN needs **3 gate-weight matrices** per side (update/reset/candidate, GRU-like), not 2.
3. With 3 separately-allocated weight matrices: `[ASSERT-FAIL](ptr(A)==ptr(B))`, where the two pointers were exactly `weight_h[0] + (hdim×hdim×sizeof(short))` and `weight_h[1]` — the function requires `weight_x`/`weight_h` to each be **one single contiguous allocation**, with the per-gate pointers being offsets into it (a batched-GEMM layout assumption), not three independent `xpu_malloc` buffers.

**With all three fixed, the call actually dispatched for real** — no more asserts. `XPUAPI_DEBUG=1` showed a legitimate internal decomposition running on `api::kXPU1`: `sequence_to_batch` → `findmax` → three `fc_fusion` calls (one per gate) → `batch_to_sequence`. This is a meaningfully different outcome from `*_unit_fusion`'s immediate, unconditional "not implemented" asserts above — `grnn_cell`'s orchestration logic genuinely exists and runs for xpu1.

**But it doesn't complete correctly.** The first clean run returned `grnn_cell ret=0` (success) but then `xpu_wait()` failed with the same `-713 "Device abnormal due to previous error"` seen elsewhere in this work — initially suspected to be residual contamination from earlier `timeout`-killed attempts (a known artifact, not a `grnn_cell`-specific bug). Reloaded the driver for a clean state and ran it exactly once more: this time `dmesg` logged a **genuine hardware-level fault during the run** — `kunlun: [WARN] xpu0: sse exception err=400000` and `kunlun: [WARN] xpu0 xtq6: task fifo overflow` — followed by the *next* allocation call failing with `(802) Hardware module exception`. This is a real silicon/firmware-level fault, not a software validation rejection, and notably **worse** than the clean `*_unit_fusion` rejections: those failed instantly and harmlessly; this one actually disturbs the device.

**Recovery needed more than a driver reload this time.** A module hot-reload alone left the device unable to complete the standard GEMM benchmark (`benchmarks/xpu_perf_test`) — it first hung for ~10 minutes (well past its normal ~90s runtime, with no new `dmesg` errors during the hang) and then, on a second attempt, returned `OOM` on every GEMM case. A **full reboot** was required to fully restore the device to its normal, verified-healthy state (pattern tests pass, GEMM numbers back to baseline — FP32 large 7730 GFLOPS @ 53.68%, FP16 large 19,101 GFLOPS @ 33.16%, INT8 correctly unsupported). Whether the OOM/hang was itself downstream of the `grnn_cell` hardware exception (most likely — the sequence of events lines up) or a separate accumulation of unfreed test-program allocations isn't fully disentangled; either way, a full reboot was the fix, not just a module reload.

**Conclusion: `grnn_cell` is a qualitatively different and more concerning finding than `*_unit_fusion`.** The API is real, its orchestration logic runs on xpu1, and its undocumented calling convention is now known precisely — but actually dispatching it (at least with this test's specific shape/LoD/weight configuration) triggers a genuine hardware exception that required a full reboot to clear, not just a clean "unsupported" error. **Do not casually retest this without being prepared to reboot the host.** Not yet determined: whether this is a fundamental xpu1 hardware/firmware limitation for `grnn_cell` specifically, or something fixable by a different parameter configuration (different shapes, a different `TGEMM`/dtype combination, or avoiding whatever in this exact LoD/sequence-length combination triggered the "task fifo overflow"). This card's CTR/ranking-workload story is now *less* promising than the pre-test static analysis suggested, not more.

```
LnkSta: Speed 8GT/s (downgraded), Width x8
```
`LnkCap` confirms the K200 is a PCIe **Gen4** x8 device (matches this repo's own documented spec), but `LnkSta` — what's actually negotiated — is **Gen3** (8GT/s), with `lspci` itself flagging it `(downgraded)`. Width is unaffected (still x8); only the per-lane signaling rate is halved.

**Root cause: the host CPU has no Gen4 PCIe controller at all — this is a hard silicon limit, not a misconfiguration.** The R730 host's CPU is an **Intel Xeon E5-2682 v4** (Broadwell-EP, launched 2016). Broadwell-EP's integrated PCIe root complex implements **PCIe 3.0 (8GT/s) only**; Intel didn't ship a Gen4-capable root complex until Ice Lake-SP (~2021). The link negotiates to the highest speed *both* ends support — the K200's own `LnkCap2` lists support down to 2.5GT/s, so it cleanly falls back to Gen3 rather than failing to train. No BIOS setting fixes this; it would need different host hardware (a newer CPU generation with native Gen4 PCIe) to get this card running at its rated speed.

**Topology confirms this is the whole story, nothing else degrading it further:** `lspci -tv` shows the card directly under the CPU's own root port (`[0000:80]-02.0-[82-83]--00.0`, NUMA node 1) with **no intervening PCIe switch** in the path — a separate Renesas SH7758 PCIe switch pair visible elsewhere in the topology (`06:00.0`/`07:00.0`, both themselves only Gen1 x1 — likely BMC/management-related) sits on an unrelated branch, not between the CPU and the card.

**The numbers check out cleanly against this explanation:**
- PCIe Gen3 x8 theoretical (128b/130b encoding): 8 × 8GT/s × (128/130) / 8 ≈ **7.88 GB/s** unidirectional. Measured ~5.3–6.3 GB/s is ~70–80% of that — a normal real-world efficiency.
- PCIe Gen4 x8 theoretical: 8 × 16GT/s × (128/130) / 8 ≈ **15.75 GB/s**. The repo's originally-documented peak (~10.1–12.9 GB/s) is ~65–80% of *that* — the same efficiency band, just at double the link speed.
- The ratio between the two peaks (~2x) matches the Gen3-vs-Gen4 raw rate ratio (8GT/s vs 16GT/s = exactly 2x) almost exactly.

**Conclusion: this answers the open question's "whether original S4–S9 numbers came from different hardware" guess — yes, they almost certainly did** (a host with a Gen4-capable root complex, i.e. newer than Broadwell-EP). The DMA path itself is not regressed — it's delivering the expected efficiency for the PCIe generation it's actually got. Not pursued further: swapping the card into Gen4-capable host hardware to confirm empirically would need different physical hardware, not available in this session.

## K-means clustering: confirmed working end to end (2026-10-19)

**Conclusion: this is now confirmed, not just plausible.** Every op in the chain this repo's own static analysis predicted was genuinely available dispatched correctly and computed a bit-exact result, wired together as one real program — the strongest form of evidence used anywhere in this doc (stronger than the OCR/CRNN tests above, which tested the recurrent layer in isolation rather than a full assembled pipeline). ## Custom xpu1 kernel proof-of-concept: real progress, one open gap (2026-10-19)

Went past "the compiler is obtainable" to actually writing, compiling, and attempting to run a hand-written xpu1 kernel on the real card. Full writeup, kernel source, and a runnable launcher example: [`docs/research/20261019-xpu1-custom-kernel-poc.md`](docs/research/20261019-xpu1-custom-kernel-poc.md).

**Confirmed, for the first time:**
- This repo's bundled plugin build system (`xdnn-ubuntu_x86_64/plugin/`) already treats xpu1 as a first-class target (`search_and_compile_kernel("xpu1")`, `--xpu-arch=xpu1`) — just with no example kernel shipped for it.
- A genuinely new (not xdnn-provided) xpu1 kernel compiles cleanly with the real, publicly-downloaded XTDK compiler.
- xpu1 lacks xpu2+'s SIMD vector ALU entirely — confirmed two ways: `cluster_simd.h` is guarded to `__XPU3__`/`__XPU4__` only, and the xpu2 example's `__simd__`/`svadd_float32x16` constructs fail to compile for `--xpu-arch=xpu1` ("unsupported... compiling for generic"). Basic cluster primitives (`GM2LM`/`LM2GM`/`core_id()`/`mfence()`) work fine for xpu1 — only the newer vector extensions are generation-gated.
- `xpu_set_device`/`xpu_malloc`/`xpu_memcpy`/`xpu_stream_create` and the kernel launch call itself all succeed cleanly against real hardware (correct device addresses, correctly resolved device symbol name).

**Not yet confirmed (as of 2026-10-19):** the kernel completing. `xpu_wait()` doesn't return within the tested window, reproducibly, across kernel variants including one deliberately simplified to rule out a self-inflicted infinite loop. Leading hypothesis at the time: every other working kernel-launch example in this SDK goes through `baidu::xpu::api::Context` (`xdnn::create_context()`), not raw XPURT calls as this proof-of-concept does — `Context` construction may perform one-time compute-side initialization this bare-metal approach skips. Testing that hypothesis is blocked by a separate, unresolved toolchain issue: XTDK's 2021-era clang 15 vs. this host's very new glibc/libstdc++ hits two independent `__float128` incompatibilities when compiling anything that pulls in the full `xdnn.h`; one was worked around, the other wasn't (see the linked doc for both, including the exact failing header lines and what was tried).

**Also discovered in passing:** force-killing a process mid-kernel-dispatch can leave the device's compute-launch state "abnormal" (`ioctl() fail, (713) Device abnormal due to previous error`) in a way that persists until the driver is reloaded — confirmed the DMA/memory path (`tests/test_host_alloc`/`test_pageable_verify`) is unaffected throughout, so this is isolated to the compute-dispatch path specifically.

**Update 2026-10-20 — the toolchain blocker is solved, the Context hypothesis is refuted, a better hypothesis found, and a more serious risk confirmed.** Full details, exact flags, and kernel source: see the linked doc's "Update 2026-10-20" section. Summary:
- **`__float128`/`<limits>` solved**: the real guard (`#if defined(__FLOAT128__) || defined(__SIZEOF_FLOAT128__)` in glibc's `bits/c++config.h`) is tripped because XTDK's clang predefines *both* macros for this target even though its xpu1 backend can't codegen the type — a frontend/backend mismatch in Baidu's fork, not a glibc/libstdc++ bug. Fix: add `-U__FLOAT128__ -U__SIZEOF_FLOAT128__` alongside the already-known workaround. The full `xdnn.h`, including `Context`/`create_context`/`destroy_context`, now compiles and links clean under XTDK for `--xpu-arch=xpu1`.
- **Context hypothesis: tested directly, refuted.** A `Context`-based launcher (`ctx->get_stream()`, which is `nullptr` on a fresh `Context` — a default `Context` has no stream until `set_stream()` is called) hit the identical hang as the bare-XPURT version. `Context` construction is not the missing piece.
- **Better-supported hypothesis found**: the SDK's own one shipped, working reference kernel (`add1.xpu`/`add2.cpp`) partitions work across threads via `core_id()`/`core_num()`/`cluster_id()`/`cluster_num()` with a striding loop and an early-return guard; this proof-of-concept's kernel has none of that — every thread redundantly runs the full-range loop. Bumping thread count alone (`<<<1,64,...>>>`, no partitioning added) still hung, ruling out "just launch more threads" as a one-line fix but not disproving the hypothesis. **Not yet tried**: adding real `core_id()`/`cluster_id()`-based partitioning to the kernel body.
- **More serious risk confirmed**: a second timeout left the device's compute PD in a persistent `state=ERROR` (`/proc/xpu/dev0`) that a plain driver reload did **not** clear this time (unlike the first, lighter corruption noted above) — a full reboot was required. **This elevates hand-written custom-kernel testing to the same risk class as `grnn_cell`**: never assume a reload is sufficient recovery; verify with a real GEMM run, not just `probe_error`/DMA tests, and expect that a full reboot may be needed.

**Update 2026-10-20 (continued): the partitioning hypothesis tested too — also refuted.** Built the partitioned kernel (`core_id()`/`cluster_id()`-based striding, matching the reference's structure) and launched it exactly as the reference does (`<<<ctx->ncluster(), 64, stream>>>`, confirmed `ncluster()`=4 at runtime). **Identical hang.** Three independent variables tested across this work (bare XPURT vs. `Context`; degenerate vs. matched launch config; unpartitioned vs. partitioned kernel) — none changed the outcome. **Correction to the comparison basis**: the "reference" kernel used throughout (`add1.xpu`) is `namespace xpu2`-wrapped — it targets a *different hardware generation*, not xpu1. There is no shipped, confirmed-working example of a raw custom kernel completing on xpu1 anywhere in this SDK. Updated leading hypothesis: raw custom-kernel dispatch/completion-signaling may simply never have been implemented or validated for xpu1 specifically (xpu2+ got a shipped example; xpu1 did not) — a firmware/runtime generation gap, not a mistake in kernel structure or launch config. This time the device stayed healthy after the timeout (confirmed via a real GEMM run) with no reload/reboot needed — state corruption on a timeout looks intermittent, not deterministic. Full details: see the linked doc's "Update 2026-10-20 (continued)" section.

**Correction (found 2026-10-20, during the `fft` testing below): that "healthy, no reload needed" conclusion was wrong, and the verification method itself had a real gap.** The `add_two_v2` task was in fact still sitting, wedged, in hardware task queue `tq6` the entire time (`/proc/xpu/dev0/tqinfo` showed `tq6: state=HANG`, ten tasks deep, the original `add_two_v2` task still at its head) — a later, unrelated test collided with it. The GEMM run that seemed to confirm health had simply been scheduled onto a different, still-free queue (`tq0`–`tq5`/`tq7` were all idle); it never touched `tq6`, so it couldn't have revealed the problem. **Running the full GEMM suite is not sufficient to confirm the device is genuinely clean after a custom-kernel test** — it only proves *some* queue works. The real check is `cat /proc/xpu/dev0/tqinfo` and confirming all 8 queues report `NORMAL`, not just that one workload happened to succeed. A plain driver reload did clear the wedged queue once this was found (confirmed via `tqinfo` showing all 8 `NORMAL`, not assumed) — a full reboot was not needed this time, but given the method that "confirmed" this previously was broken, this specific instance's severity is itself less certain than stated above.

**Checked whether this could be power-related (asked 2026-10-20):** the test host's PCIe slot reports `SlotPowerLimit 25W` — low for an accelerator card, worth a physical check (R730 risers can have jumper-configurable power modes). At the time, the fault pattern argued against power as the cause: the heaviest workload tested (full GEMM, run dozens of times) had never faulted, while the thing that hung was trivially light compute; zero PCIe AER/link-error events were ever logged; `reset_count` stayed at 0. **Correction, later the same day**: GEMM did eventually hit the identical fault once (see "Audio/speech pipeline" below) — but only after a long, heavy same-day testing session, not on any of its dozens of earlier runs. If this were simple power-delivery insufficiency under heavy draw, GEMM should fail often and early, not rarely and only after extensive prior activity — so this still argues for a cumulative/session effect over a pure power explanation, just not as cleanly as originally stated. Not fully closed out quantitatively either way (no live power telemetry was pulled — the driver's power monitor is internal-ioctl-only).

## Audio/speech pipeline: confirmed working end to end (2026-10-20)

Wired the per-frame FFT magnitude spectrum, `lstm_inference`, and a dense+sigmoid classifier head into one real program — the first "whole pipeline" test for this workload category, not isolated ops. Full source: [`docs/research/20261019-xpu1-op-testing-examples.md`](docs/research/20261019-xpu1-op-testing-examples.md#9-audio-pipeline-fft--lstm--dense-classifier--confirmed-working-end-to-end).

**One methodology lesson along the way, worth keeping**: an early version of this test, run in a loop without calling `xpu_free` on intermediate buffers, intermittently faulted (`sse exception`/`task fifo overflow`, all 8 queues `HANG`, occasionally escalating to the standard GEMM benchmark itself and needing a full reboot to clear). This reverses the earlier "real hardware-level exception" finding. The CTR/ranking workload category is now meaningfully more promising than either the original static analysis or the first hardware test suggested.

**The custom hand-written kernel (`add_two_v2`) still does not complete.** Retested with a cleaner failure mode than before (`dmesg` silent, one harmless orphaned task, no hardware fault) — a genuinely different symptom from the destructive class seen earlier with `grnn_cell`. Followed up with an `strace`-level ioctl trace comparing this launch against a known-working `xdnn::add<float>` call: both issue the identical submit-then-wait ioctl pair; the working call's wait returns `0` immediately, this kernel's wait blocks forever (`ERESTARTSYS`) on the exact same call — the driver's dispatch mechanism is provably identical in both cases, only the kernel's own completion signal differs. Checked the official plugin build system (`CMakeLists.txt`) for anything the manual compile might be missing and tested both real differences found (`-Werror` on the device compile; `--xpu-host-only` instead of `--xpu-arch=xpu1` on the host compile) — neither changed the outcome. Five independent variables now tested and ruled out in total (`Context` vs. bare XPURT, launch config, partitioning, `-Werror`, `--xpu-host-only`).

**New risk finding**: repeated exposure to this hang caused the standard GEMM benchmark to start hanging reproducibly, with a driver reload no longer sufficient to recover — a full reboot was needed. Treat every attempt at this kernel path as carrying that cost.

**Conclusion**: raw `<<<>>>` kernel dispatch/completion-signaling likely was never implemented or validated for xpu1 — this is now a thoroughly exhausted investigation from the software side. What's left is a device-side disassembly session or input from Baidu, not another build variant to try.

## K200 vs. host CPU: where the card actually wins, and what FP32/FP16 GEMM are for (2026-10-20)

Prompted by a direct question about what this card is better at than the test host's own CPUs. Grounded in numbers already measured elsewhere in this doc (`xpu_perf_test 0`'s GEMM sweep, the bandwidth shortfall root-cause) plus this session's own `lscpu`/`numactl -H` check of the host — **no new CPU-side benchmark was run** (no BLAS installed on the host), so the CPU side below is a labeled theoretical estimate, not a measurement; keep that distinction in mind if this is revisited.

**Host CPU**: dual Intel Xeon E5-2682 v4 (Broadwell-EP), 32 cores / 64 threads @ 2.5GHz, AVX2+FMA only — no AVX-512 (that arrived with Ice Lake-SP in 2021) and no native FP16 compute path (F16C only converts formats, it doesn't accelerate FP16 math). Theoretical FP32 peak ≈ 32 cores × 32 FLOPs/cycle × ~2.2GHz sustained-AVX clock ≈ **~2.2 TFLOPS**; realistic achievable with a well-tuned BLAS (not installed on this host) is usually 60–80% of that, so call it **~1.5–1.8 TFLOPS** FP32 in practice.

**Card, measured** (from the GEMM sweep already in "Key benchmarks"): **FP32 ~4,500–7,800 GFLOPS**, **FP16 ~18,000–22,600 GFLOPS**, across realistic shapes (BERT-FC, ResNet, 2048–8192 square).

**Where the card wins — and it's a real, measured gap, not just marketing:**
- **FP16 GEMM is the single biggest win**: ~18,000–22,600 GFLOPS measured vs. the CPU's complete lack of native FP16 acceleration (FP16 "work" on this CPU generation just runs at FP32 throughput after conversion) — roughly **10×+** the CPU's realistic FP32 ceiling, in a precision the CPU can't accelerate at all.
- **FP32 GEMM** is still a solid **3–5× win** (~4,500–7,800 vs. ~1.5–1.8 TFLOPS realistic).
- Every building block already confirmed correct on this card — BERT/ERNIE attention, K-means, the YOLO-style conv unit, `lstm_inference`/`bilstm_inference`, the NCF forward pass — is GEMM or `fc` underneath, so this advantage is inherited by all of them once the problem is large enough to amortize dispatch and transfer cost.

**Where the CPU wins outright, not just on latency** — a hard capability gap, not a speed tradeoff: anything using an op this card's `libxpuapi.so` build doesn't implement for xpu1 at all. LLM transformer serving kernels (RoPE/SwiGLU/RMSNorm/paged-attention, gen-gated to `xpu2::`/`xpu3::`), graph scatter-add/SpMM (absent regardless of generation), CTC-loss training, `conv2d_transpose`, `roi_pool`, and the hand-written custom-kernel path (confirmed broken — dispatch never completes) all simply don't run on the card; the CPU is the only option. Small/latency-sensitive/one-off jobs also favor the CPU: the card's PCIe link only negotiates Gen3 (~5–6 GB/s H2D/D2H, root-caused to the host CPU's own lack of a Gen4 controller — see "Bandwidth shortfall" above), so anything too small to amortize dispatch+transfer overhead is faster run directly on the CPU. INT8 GEMM throughput is inconclusive at the full-benchmark level (`xpu_perf_test`'s INT8 sweep errors with `"not supported"`), even though INT8 (`signed char`) dtype dispatch does work at the individual-kernel level elsewhere (the YOLO-style conv unit test) — not a clean comparison point either way without more digging.

**What FP32 GEMM is for, concretely, on this card:**
- Correctness-critical or reference work, where the result needs to match a CPU/hand-computed value exactly or near enough — the BERT/ERNIE attention projections and the K-means distance computation were both run in FP32 specifically so they could be checked against hand-computed expectations exactly.
- General-purpose dense linear algebra that isn't a neural net at all (the "bare compute/RNG coprocessor" capability row) — simulations, batch distance/similarity computation, anything matmul-shaped.
- Any op whose xdnn wrapper only has a clean FP32/all-`float` instantiation — several ops tested this session (`interpolate2d`, the one working `conv2d_transpose` combo, `roi_align`) were only tested as `<float>`.

**What FP16 GEMM is for, concretely, on this card:**
- Inference throughput where some precision loss is tolerable — the card's actual strength, and in some cases the *only* implemented path: the YOLO-style conv unit test used FP16 (`conv2d_fusion` FP16/int8) specifically because the all-`float` variant hit a clean `XDNN_UNIMPLEMENTED`.
- Neural-network inference generally — matmul-heavy layers (fully-connected/linear, attention projections, conv lowered to GEMM, LSTM/BiLSTM gates, the NCF dense head) tolerate FP16's ~3-decimal-digit precision fine, which is exactly what was confirmed in the YOLO conv unit result (matched a CPU reference within FP16 rounding tolerance, max diff ≈0.0005–0.009).
- Anything bandwidth- or memory-bound rather than purely compute-bound — FP16 halves data moving through the PCIe link (already the card's weakest point) and through on-device memory.
